# 账户归属审计报告

日期：2026-10-12。问题章节记录重构前基线；最终行为与验证见末尾交付状态。审计基线：`dba7144` 加工作区中已完成的跨账户成交展示修复。报告中的缺陷描述是修复前的行为；重构后的结果将在末尾更新。

## 结论

需要重构，但不宜一次推翻全部账本。问题不只是“未归属”这个名字：项目把账本所属账户、成交目的账户、计划来源账户和份额账户标注混在同一套界面与操作里，却没有统一的归属迁移规则。

本轮确认四类可复现问题，其中最严重的是**历史归类会断开计划与成交的关联，并允许重复补录成交**。还确认了份额标签与账本的展示口径不同，以及两种买入入口成交后留在不同账户的行为。

没有证据表明你先前选中的买入账户没有保存，也没有据此认定你的真实记录已经损坏。本轮复现全部使用虚构数据。

## 当前“归属”的实际含义

| 层次 | 当前权威数据 | 当前行为 |
| --- | --- | --- |
| 真实记账位置 | `BrokerageAccountPortfolio` 中的交易列表 | 持仓数量、成本和已实现盈亏按这个账本重放 |
| 成交时所选账户 | `PositionTransaction.brokerageAccountID` | 新买入写入所选命名账户；旧记录缺失时继承所在账本 |
| 计划来源 | `TradePlanExecution.sourceAccountID` | 跨账户成交可以回连原计划；旧值缺失时按成交当前账本推断 |
| 卡片账户标注 | `PositionPortion.brokerageAccountID` | 改卡片归集、账户总览及部分预算分组，不搬成交账本 |
| 当前页面账户 | `activeBrokerageAccountID` | 控制持仓查看和部分操作上下文；现在不再过滤实际成交显示 |
| 未归属 | `BrokerageAccountID.unassigned` | 同时承载旧历史、计划来源、页面状态和部分预算，职责过多 |

因此，选择了真实成交账户，并不意味着旧持仓、旧计划来源和当前页面也自动变成那个账户。这是此前“明明选了账户，仍看到未归属”的直接原因。

## 已确认缺陷

### R1 · P1：归类会断开计划成交关联，进而重复记账

有两条独立路径，根因相同：归类搬了对象，却没有维护计划来源引用。

**整体账本归类。** 未归属账本中有旧持仓和计划，计划已经在融资账号成交。把原账本归类到另一个空的命名账户后，计划迁走了，外部成交仍保存 `sourceAccountID = unassigned`。新账本里的计划再也找不到原成交。

虚构复现：计划已成交量从 **10 变成 0**，剩余量变成 10；原成交没有被删除。

**部分成交归类。** 旧的同账本成交没有显式 `sourceAccountID`。只迁出这笔成交，计划留在原账本。迁出后，原来“继承原账本”的缺失字段被重新解释成“继承目标账本”，原计划丢失这笔成交。

虚构复现：已完成计划被重新视为可补录；再补录后，目标账本数量从 **10 变成 20**。这是本地持仓记录重复，并非执行了第二次券商交易。

证据入口：`WatchlistStore.assignBrokerageRecords`、`WatchlistStore.transactionsForPlan`、`TradePlanExecution.sourceAccountID`、`TradePlanEntry.canBackfillFill`。迁移前后进度的实际输出保存在 [基线验证日志](../../audit/ownership-2026-10-12/baseline-validation.log)。

建议：把归类作为整个快照的原子操作。部分迁移冻结迁出前的计划来源；整体迁移更新所有账本中的相关引用，按标的、计划 ID、原来源账户精确匹配，不能仅按 UUID 改全部计划。

### R2 · P2：融资历史能被归类到只支持普通买入的账户

新买入和份额标注会拒绝“萌萌账号 + 融资买入”，但是历史归类未执行同等检查。旧融资记录能整体迁入萌萌账号，同时保留融资资金来源。

虚构复现：归类返回成功；萌萌账本内存在 `fundingSource = margin` 的交易，尽管 `permitsBuy(.margin)` 为 false。

证据入口：`WatchlistStore.assignBrokerageRecords`、`BrokerageAccountID.permitsBuy`、`WatchlistStore.setPositionBrokerageAccount`。

建议：归类前验证明确的资金来源与目标账户是否兼容；冲突时拒绝并解释。不要为了让归类成功，自动把旧融资事实改成普通资金。

### R3 · P2：计划成交入口可绕过“新买入不能落到未归属”的规则

`recordBuyTransaction` 会拒绝未归属目的账户；`recordTradePlanFill` 则只在调用参数 `brokerageAccountID` 非空时执行完整账户检查。参数为空且当前账本为未归属时，仍能新建普通资金买入。

虚构复现：启用多账户后，计划买入成功写入未归属；同条件的普通买入接口拒绝。

**可达范围：Core 公共入口已经复现；当前买入界面要求选择命名账户，MCP 普通买入也会拒绝未归属。** 不能把这个 Core 防线缺口说成所有正常界面都会写错账户。

建议：先解析实际目的账户，再统一校验。是否显式传了参数，不应决定是否执行账户规则。旧数据读取和迁移仍须兼容。

### R4 · P2：归类最后一笔时，界面会切换模式而无法完成

界面将“所选成交恰好等于所有剩余成交”自动改成“整体账本”；剩一笔时又不再提供“选择成交”。但整体账本归类遇到同标的目标账本已有交易时会拒绝。

虚构复现：先成功迁出第一部分，最后剩下 5 股；最后一步被改走整体账本路径，遭到拒绝，5 股继续留在未归属。目标已存在该标的时，也可能一开始就无法整体归类。

证据入口：`BrokerageAccountClassificationSheet.toggle(_:in:)` 的 `wholeLedger = ids == allIDs`、选择菜单的 `count > 1` 条件，以及 Store 对整体迁移的目标历史冲突保护。

建议：整体账本和所选成交必须是明确模式，不由数量猜测。最后一笔仍能使用成交模式；整体模式目标存在计划、事件等冲突时保留原保护；所选成交模式保留目标资料并独立校验，允许最后一笔整理到已有账本。

## 已确认的模型和展示问题

### D1：总览按卡片标签，持仓详情按账本

虚构复现：给未归属账本的 10 股卡片标注融资账号后，`positionAccountQuantities` 归集到融资账号；融资账号真实交易账本仍为空，未归属账本仍持有 10 股。

`BrokerageAccountOverviewReader` 读取份额归集，`MainHoldingsView` 和持仓详情读取原账本。两边可以给同一个账户显示不同数量。

这是既有设计明确允许的行为，并非这次发现卡片误搬了成交；但它使“账户归属”不再只有一个用户能理解的含义。卡片上选择了账户，也不代表该账户的成交账本已完成归类。

### D2：普通买入与计划买入成交后的页面行为不同

普通买入保存后调用 `selectBrokerageAccount(实际账户)`；计划买入只有在“成交并打开复盘”时才调用。普通记录计划成交后，页面可能继续停在原计划的未归属账本。

这是用户困惑的重要来源，不能当作成交账户没有保存。建议统一成交后的目的地上下文，并确保部分计划和历史仍然可见。

### D3：计划预算没有明确的拟执行账户

计划保存在来源账本，预算通常按 `TradePlanEntry.accountID` 分组；实际买入账户却可以在成交时另选。`PoolBudgetInput.projectionGroups` 默认使用计划来源，仅绑定卖出份额的计划按卡片归集分组调整。

因此，未归属来源的计划准备在融资账号执行时，预算可能仍在未归属组计算。这不代表现金隔离算法错误，而是执行账户信息尚不存在，模型却先给出了账户预算。

本项为源码确认的口径缺口；未录入真实现金进行操作复现。后续应增加明确的拟执行账户；未选时显示“执行账户待确认”，不能把未知账户当作某个账户的确定现金缺口。

## 核对后未认定为缺陷的内容

- 旧历史初始留在未归属，不猜测所属券商，是合理的迁移保护。
- 每个账本独立重放成本、手续费和已实现盈亏是正确边界；不能为了全局显示成交，把多个账户混成一个成本账本。
- 当前普通买入界面和 MCP 普通买入已拒绝未归属新买入；问题是 Core 入口规则尚未统一。
- 同步合并对跨账户重复交易 UUID 会报告账户冲突，线格式也做跨账户交易查重；本轮没有证据证明正常同步会悄悄复制成交。
- 完整备份与同步覆盖全部账本；可移植自选归档是单账户范围，不能把它当作跨账户完整备份。
- 子代理提出的 Agent 无改动更新会偷偷改元数据的候选不成立：`alreadyApplied == true` 时不会调用 Store 更新。本轮另外保证有实际修改的 Agent 计划编辑保留默认执行账户等它未编辑的元数据。账户列表包含未归属，也是已有兼容设计，不能单凭出现这一项判定串账。

## 为什么需要重构

错误出现的位置是领域边界：一个操作在更新账本，另一个模块靠账本位置解释缺失字段，第三个模块按卡片标签算账户金额。任何一边补一个分支，都可能让另一边继续误解。

建议保留经过验证的成本算法和同步骨架，集中归属规则与归类事务，通过统一投影将计划执行意图与来源身份分开。“未归属”应收敛为待确认历史状态，而不是默认新业务账户。

具体开发设计和验收标准见 [重构设计](../design/ownership-refactor.md)。

## 2026-10-12：计划展示补充修复

- 按用户要求统一买入红色、卖出绿色；计划列表与图表虚线共用方向色，适配明暗主题。
- 图表此前只读取当前账本的计划，列表则包含全账户计划，造成缺线。现在图表与列表使用相同的全账户读取，并按来源账户区分图表身份；原持久化计划 ID 保持不变，编辑仍打开来源计划。待成交线采用剩余数量，已完成成交不会因旧原始状态继续显示成待成交线。
- 两个待成交状态此前分别是静态标签和菜单。现在统一为相同菜单，操作前选择计划真实来源账本；无法选择时不执行操作。
- 39 项 PulseUI 测试、112 项原生计划交互检查通过。隔离原生验收覆盖三个账户、同 UUID 的两条跨账户计划、19 张渲染；已检查明暗主题的两条可见虚线与方向颜色。
- 日常应用已更新，安装签名与二进制验证通过。实际界面确认两条卖出计划线、方向颜色和待成交菜单一致；新增计划线打开正确的来源计划。验收取消草稿并恢复原账户视图，没有保存真实成交或计划修改。
